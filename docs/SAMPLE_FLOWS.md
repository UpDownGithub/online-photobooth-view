# 촬영·사진 처리·WebRTC 예제

기존 화면 코드에 연결해 읽을 수 있도록 세 흐름을 추가했습니다. 원본 로직을 발췌·재구성한 **오프라인 예제**이며, 운영 서비스를 실행하는 서버나 통신 계층은 없습니다. 입력은 가짜 참가자와 생성한 색상 이미지입니다.

## 1. Ready부터 결과 확인까지

[shooting-session.cjs](../backend/modules/shooting/shooting-session.cjs)는 준비 확인, 참가자 순환 촬영 순서, 경과 시간에 따른 카운트다운, 컷 완료와 리뷰 전환을 담당합니다.

```text
LOBBY → 모두 Ready → COUNTDOWN → SHOOTING
                             ↑       ↓
                             └─ 다음 컷
                                     └─ 마지막 컷 → REVIEW → 다시 촬영 → LOBBY
```

- 2명이 4컷을 찍는 경우 촬영 순서는 A → B → A → B입니다.
- 카운트다운은 호출 횟수가 아닌 시작 시각과 현재 시각의 차이로 계산합니다.
- `advance()`는 한 번에 한 단계만 진행합니다. 실행이 늦어져도 아직 캡처하지 않은 컷들을 건너뛰지 않습니다.
- 반환 상태는 복사본입니다. 재촬영마다 로컬 `generation`을 바꿔 이전 인코딩 결과를 구분합니다. 이 숫자는 인증 토큰이 아닙니다.

원본 `rooms/service.js`의 상태 전환과 `shooting.runtime.js`의 순서를 바탕으로 구성했습니다. 메모리 매니저는 단일 세션 클로저로, 타이머는 주입한 시계와 명시적인 `advance()` 호출로 바꿨습니다. DB 집계, 방 만료, 참여 인증과 Socket.io 전파는 제외했습니다. 원본 런타임에서 보장하던 순서·시간 조건 일부를 예제 함수에서도 검사합니다.

## 2. 캡처 → 압축 → 전달 → 합성

```text
SHOT_STARTED   → captureFrame(호출부가 고른 video) → 원본 캔버스 보관
SHOT_COMPLETED → encodeShotForUpload              → JPEG Blob
               → retryShotUpload(전달 콜백)       → 메모리 Buffer
REVIEW         → composeReview                    → WebP Buffer
```

| 파일 | 유지한 구현과 공개용 변경 |
| --- | --- |
| [capture-frame.js](../frontend/src/media/capture-frame.js) | 원본 카메라 캡처의 중앙 정사각형 크롭·업스케일 방지·거울 반전. DOM 검색과 카메라 상태 조회는 입력 `video`, `mirrored`로 바꾸고 캔버스 생성 함수를 주입 |
| [shot-upload.js](../frontend/src/media/shot-upload.js) | 원본의 독립 압축·재시도 모듈을 그대로 사용. JPEG 품질을 단계적으로 낮추고 해상도를 유지. HTTP 호출은 없음 |
| [shot-pipeline.js](../frontend/src/media/shot-pipeline.js) | 캡처 시점과 인코딩 시점을 나누는 원본 호출 흐름을 콜백으로 재구성. 같은 완료 이벤트는 한 작업을 공유하며, 인코딩 후 이전 세션이면 전달하지 않음 |
| [compose.cjs](../backend/modules/render/compose.cjs) | 원본의 슬롯 배치, cover 리사이즈, 프레임 마스크·헤더, 오버레이, 필터 레시피와 회전 스티커 경계 크롭을 발췌·적용. 경로·주소 대신 미리 준비한 래스터 Buffer만 받음 |

압축은 매번 최초 캡처 픽셀에서 시작합니다. 5 MiB 이하여야 전달하고 모든 품질 단계에서 초과하면 `SHOT_COMPRESSION_LIMIT`으로 끝냅니다. 리사이즈로 화질을 추가로 낮추거나 무한히 재시도하지 않습니다. 이 예제의 전달 콜백은 네트워크를 사용하지 않습니다.

합성은 기존 [레이아웃](../backend/modules/frames/layouts.cjs)과 [필터](../backend/modules/filters/filters.cjs)를 재사용합니다. 2명·2×2에서는 촬영 순서와 결과 배치 순서를 분리해 `[0,1,3,2]`로 놓습니다. 무필터 컷에 리뷰에서 고른 필터를 적용하고, 프레임 다음에 스티커를 얹습니다. 최종 WebP는 알파를 유지하고 원본 메타데이터를 복사하지 않습니다.

파일·URL·SVG 입력은 받지 않습니다. 입력 크기, 픽셀 수, 단일 이미지 형식, 스티커 수·좌표를 검사합니다. 프레임과 스티커 자산을 자동 탐색하거나 저장소에서 내려받지 않습니다. 없는 컷은 어두운 칸으로 표시하며 원본의 누락 컷 안내 글씨는 생략했습니다. 합성 예제의 검사는 운영 업로드 검사를 대체하지 않습니다.

## 3. WebRTC의 비동기 순서 문제

[peer-session.js](../frontend/src/rtc/peer-session.js)는 **한 쌍의 peer 협상**만 다룹니다.

- 원격 설명이 설정되기 전에 들어온 ICE 후보를 보관하고, 설명 설정 후 순서대로 적용합니다.
- 후보 하나가 실패해도 뒤 후보는 계속 적용합니다. 오류 콜백에는 후보·SDP 내용 대신 고정 코드만 넘깁니다.
- offer 생성은 지정된 한쪽만 맡습니다. 두 쪽이 동시에 `connect()`를 호출해도 올바른 역할 설정이면 offer는 하나입니다.
- 비동기 설명 변경을 직렬화하며 연결을 닫은 뒤 끝난 작업은 신호를 보내지 않습니다.
- 대기 후보는 최대 128개입니다. 닫을 때 대기 목록과 이벤트 핸들러를 정리합니다.

원본 `services/rtc.js`의 후보 대기와 한쪽 offer 전략을 바탕으로 재구성했습니다. 원본의 입장 이벤트에 따른 역할 결정은 `initiator` 인자로, peer 생성과 신호 전송은 콜백으로 바꿨습니다. 양쪽에 같은 역할을 설정하는 잘못된 통합까지 자동 해결하는 perfect negotiation 구현은 아닙니다.

이 모듈은 peer에 트랙을 붙이거나 ICE 설정을 가져오지 않습니다. 소켓 라우팅, 신호 발신자 인증, 실제 참가자 조회, TURN 발급, 단절 복구·재협상은 포함하지 않습니다. `createPeer`는 준비된 peer를 반환하고 `sendSignal`은 상대에게 보낼 신호를 큐에 넣는 역할입니다. 테스트에서는 브라우저 peer 대신 가짜 객체와 메모리 큐를 사용합니다. 실제 서비스에 붙이려면 이러한 경계를 별도로 구현해야 합니다.

## 연결 예제와 검증

[shooting-flow.cjs](../examples/shooting-flow.cjs)는 두 가짜 참가자가 Ready를 누른 뒤 네 색상 이미지를 순서대로 캡처·인코딩·전달·합성합니다. 마지막 상태를 기존 `renderRoomLayout`에도 전달합니다. 이미지는 메모리에서만 처리하며 명령 실행 시 상태와 결과 규격을 출력합니다.

Node.js 22.12 이상에서 예제용 의존성을 설치한 후 실행합니다.

```sh
npm install
npm test
npm run example
```

루트 `package.json`은 이 예제의 테스트를 위한 것이며 전체 서비스의 실행 설정이 아닙니다. `.env`, 계정, 카메라 권한, 외부 서비스 연결이 필요하지 않습니다. 테스트 코드는 [tests](../tests)에 있습니다.

- 촬영 전제조건·시간 경계·1~4명 레이아웃·재촬영·상태 복사
- 크롭·반전·압축 단계·해상도 유지·재시도·늦은 인코딩 무효화
- 네 컷의 실제 결과 픽셀 순서, 필터, 알파, 오버레이·스티커 레이어, 메타데이터 미복사
- 두 peer의 offer/answer와 먼저 도착한 ICE, 실패 후보·중복 호출·종료 중 비동기 작업
- 기존 프런트엔드와 서버의 레이아웃 계산 일치

Canvas 테스트 어댑터는 Sharp로 합성 픽셀을 인코딩합니다. 실제 브라우저의 Canvas 인코더나 기기별 카메라 동작, 실제 WebRTC 연결 품질을 검증한 결과는 아닙니다.
